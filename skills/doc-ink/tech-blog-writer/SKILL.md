# Technical Blog Writing Skill

## 1. Skill 定位

用于生成中文技术博客、AI 工具盘点、技术选型、产品测评、开发工具推荐、技术趋势分析等文章。默认为markdown格式的文件

整体风格： **个人技术博客 + 实际体验 + 技术科普 + 横向对比 ** 排版： 简洁紧凑，篇幅可控，不要分太多段落(最多不超过7段)，阅读信息密度高的原则 (ascii 的话在不影响排列观感的话，尽量横向排列)； 文章应该像一个真正做过技术实践的人在分享经验，而不是官方产品介绍，也不是新闻稿。

核心要求：

-   简洁 & 直接 & 少废话 &  有个人判断
-   不要出现具体的人名，比如有我叫xxx，统一改为 GC/张三，李四等通用名称
-   多使用表格(简洁直观)，必要时使用ASCii
-   适当使用问答方式 ， 技术概念尽量通过具体例子解释， 避免明显的 AI 生成腔，避免过度正式、过度营销
-   避免大量碎片化小标题, 大的分段标题不要超过7段, 每个大章节用“----” 分隔符分割开来
-   不要为了“结构完整”而强行增加内容
-   涉及到厂商产品的或者有明确告诉有参考链接地址的，要在厂商产品名字上增加超链接到官网，并且在最后一段 “参考资料 & 致谢” 的地方标注官网地址
-   介绍产品的时候，可以备注该产品的最新动态(有实时连接性)： 比如 介绍Claude Code的时候，在后面增加 ： 注：2026 年还有一个比较有意思的行业事件：有报道称阿里要求员工停止使用 Claude Code，并将 Qoder 作为替代方案。报道中提到，Anthropic 本身已经限制中国企业使用 Claude，而阿里内部则将 Claude Code 归类为高风险软件

# 2. 标题格式

标题尽量采用：
- 玩转XX 第一篇: XXX
- XX 技术/工具盘点：A、B、C 到底有什么区别？
- XX 实战：XXX 到底怎么选？

标题可以适当加入产品名，方便搜索和 SEO， 标题不要过度营销。例如：
	玩转AI 第一篇: AI 生态与工具盘点，千问、豆包、元宝、Qoder、Trae、Codex到底有什么区别？
	
不推荐：震撼！2026年最强AI工具全揭秘！推荐：玩转AI：国内外 AI Agent 与大模型工具盘点

# 3. 开头格式
正文开头使用加粗斜体，可以使用“💡” 作为灵感开头。主要完成三个事情：
1.  说明为什么写这篇文章
2.  列出读者熟悉的产品
3.  提出一个实际问题

比如：

💡 ***这两年 AI 编程工具越来越多。以前我们可能只用 Cursor 写写代码补全，现在又出现了 Trae、Qoder、Codex、Claude Code……每个工具都在喊 "Agent"、"智能体"。*** 

***但你用着用着就会发现一个问题：每次让 AI 做同一件事，你都得把指令从头到尾再打一遍。上周教它怎么写提交信息，这周它又忘了。更麻烦的是，有些复杂工作流——比如代码审查、Figma 转代码、生成测试——你明明已经摸索出了一套最佳实践，但没办法固化下来让 AI 反复执行。***

 ***这篇文章就从实际使用的角度，把 Skill 这东西到底是什么、怎么用、怎么写、资源在哪，一次讲透。***


开头不要直接进入定义。
优先：现象 → 疑问 → 为什么 → 本文要解决什么
而不是：什么是 XX？XX 的定义是什么？ XX 的发展历史是什么？

```

```

不要把一个简单问题拆成十几个 `###`。

# 6. 产品盘点类文章：优先使用表格

如果存在多个产品、工具、模型、平台进行比较，优先使用 Markdown 表格。例如：

```
| 厂商 | 产品 | 主要定位 | 主要用户 | 典型场景 |
|---|---|---|---|---|
| 阿里 | **千问** | 通用 AI 助手 | 普通用户、职场人 | 聊天、搜索、写作 |
| 字节 | **豆包** | 通用 AI 助手 | 普通用户、内容创作者 | 问答、写作、图片、视频 |
| 腾讯 | **元宝** | 通用 AI 助手 | 普通用户、职场用户 | 搜索、问答、总结 |
```

表格字段一般控制在：4～8 列, 不要为了信息完整加入十几列。

# 7. 产品介绍格式

产品介绍不要写成官方说明书。推荐：

```
- 千问：面向普通用户的 AI 助手

阿里的千问更接近我们传统理解中的“AI 助手”。

现在已经不只是简单聊天，而是覆盖聊天、图片和视频理解、图片生成、文档处理等多种能力。
```

核心结构：一句话定位 + 个人理解 + 实际使用场景 + 个人判断
避免：XX 是由 XX 公司推出的一款基于 XX 技术打造的……  这种内容太像产品 PR。

# 8. 问答格式

对于容易产生疑问、容易混淆的技术概念，使用：

```
#### `Q1：XXX？`
回答……

或者：

#### `Q2：为什么 XXX？`
回答……

```

问答适合解决：
-   产品之间的关系
-   技术概念区别
-   收费方式
-   为什么会出现某种现象
-   新手容易产生的疑问
-   “到底怎么选”

例如：
#### `Q1：为什么 Trae、Qoder 里面都有 Qwen、DeepSeek？`

很多人第一次使用 AI 编程工具时都会产生这个疑问。 其实这里涉及三个不同的东西：

```text
AI 应用 / AI Agent  --> AI IDE --> 大模型      
```

所以 Qoder、Trae、Cursor 不一定等于它们自己的大模型。

# 9. 问答章节推荐结构
当一个章节主要用于科普时，可以采用：
## XXX
简单引入

#### `Q1：这是怎么回事？`
解释现象
#### `Q2：它们到底有什么区别？`
表格
#### `Q3：为什么会这样？`
解释底层逻辑
#### `Q4：作为程序员应该关注什么？`

结合实际开发场景给出建议


#### 最后总结

给出一句话结论,不要每个章节(通常放在最后一个章节call-back)都强行使用 Q&A。只有当“读者确实会产生这个问题”时才使用。

# 10. 技术关系优先使用 ASCII 图
如果需要解释系统关系、产品关系、调用链，不要全部用文字。关于不涉及到明显可视化变形的，尽量按照横向排列（便于阅读），
比如：


```text
AI IDE
   ↓
AI Agent
   ↓
大模型
   ↓
Qwen / DeepSeek / Claude / GPT
```

要按照下面这种方式排列：

```
AI IDE --> AI Agent --> 大模型 --> Qwen / DeepSeek / Claude / GPT
```
或者:
```text
需求  --> 分析项目  --> 制定方案  --> 修改代码  --> 运行测试  --> 修复问题  --> 继续迭代
```

ASCII 图主要用于：

* 架构关系
* 产品关系
* 调用链
* 工作流程
* 技术演进
* 任务流程

不要为了装饰而使用。

# 11. “一句话理解”格式

当一个概念比较复杂时，先给一个简单理解。例如：可以简单理解成： **模型负责“思考”，Agent 负责“干活”，IDE 负责“提供开发环境”。**

或者：
简单理解：

```text
Qwen / DeepSeek  -->        大模型 --> Qoder / Codex -->    Agent --> Cursor / Trae -->    AI IDE 

```

这种表达优先于长篇理论解释。

# 12. 对比表的设计原则

一个表格解决一个问题。

例如：

- 产品定位表

```markdown
| 产品 | 定位 | 主要用户 | 典型场景 |
````

- 收费表

```
| 产品 | 海外个人价 | 中国区价格 | 基础额度 | 额度模式 |
```

- 推荐表

```
| 使用场景 | 推荐产品 | 推荐理由 |
```

- 模型表

```
| 模型 | 公司 | 特点 | 适合场景 |
```

不要把所有内容塞进一张表。

# 13. 价格 / 额度类内容

涉及 AI Agent、API、模型等收费时，推荐：

```
| 产品 | 海外个人价 | 中国区价格 | 每月基础额度 / Usage | 额度怎么理解 | 小 Demo | 重度开发 | 最大特点 |
|---|---:|---:|---|---|:---:|:---:|---|
| **产品 A** | **$20/月** | — | XXXX | XXXX | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | XXXX |
```

其中：

```
价格
→ 额度
→ 额度如何消费
→ 实际体验
→ 最大特点
```

是最重要的信息链。

# 14. 星级评分格式

如果使用：

```
⭐⭐⭐⭐⭐
```

必须说明评分标准。

例如：

```
**说明：**

- **小 Demo**：主要指 Spring Boot + MySQL + Redis + JWT + 多接口 + Docker + 测试等中小型项目。
- **重度开发**：主要指真实业务项目、大型代码仓库、跨模块修改、长时间 Agent 任务、Terminal / Git / Test / Debug 等场景。
- ⭐⭐⭐⭐⭐ 表示可以作为主要开发工具使用；⭐⭐⭐⭐ 表示能力较强，但通常需要更多人工 Review。
- 星级属于个人实际使用体验，不代表官方性能指标。
```

评分一定要有“**作者视角**”。

不要伪装成权威 Benchmark。

# 15. “小 Demo”与“重度开发”定义

如果文章讨论开发工具，建议把“小 Demo”和“重度开发”定义清楚。

### 小 Demo

典型：

```
Spring Boot + MySQL + Redis + JWT + 20 个左右 API + 简单前端 + Docker +测试
```

主要看：
```
能不能理解项目
能不能修改多个文件
能不能运行项目
能不能发现错误
能不能自己修复
```

### 重度开发

主要看：

```
大型代码仓库 + 跨模块修改 + 长时间 Agent + Terminal + Git + Test + Debug + 上下文管理
```

# 16. 技术产品推荐格式

当文章进入“怎么选”阶段，不再继续堆产品介绍。  直接使用：

```
### Q1：如果只是做一个小 Demo，怎么买？
如果你的需求只是： “我想试试 AI Agent 到底能不能帮我做项目。” 其实没有必要一上来就买最贵的。

| 产品 | 价格 | 适合人群 | 推荐程度 |
|---|---:|---|:---:|
| **Trae Lite / Pro** | **$3～10 / 月起** | 想低成本体验 AI IDE + Agent | ⭐⭐⭐⭐⭐ |
| **GitHub Copilot Pro** | **$10 / 月** | 日常写代码 | ⭐⭐⭐⭐ |
| **Codex** | **$20 / 月起** | 想直接体验 Agent | ⭐⭐⭐⭐⭐ |
```

然后继续：

```
### Q2：如果我是 Java 后端开发，怎么选？

| 使用场景 | 推荐 |
|---|---|
| 只是尝鲜 | **Trae** |
| 日常代码补全 | **GitHub Copilot** |
| AI IDE + 多模型 | **Cursor** |
| 长任务 / Agent | **Qoder** |
| Terminal + Agent | **Claude Code** |
| 完整开发任务 | **Codex** |
```

最后给一句：
**一句话结论：XXXX。**


# 17. 个人观点格式

文章中应该适当加入作者自己的判断。 推荐：
```
笔者(后端&架构)的XX使用策略：
```

然后表格：

```
| 使用场景 | 推荐 |
|---|---|
| 只是尝鲜 | **A** |
| 日常开发 | **B** |
| 复杂项目 | **C** |
```

或者：

```
我的理解是： XXXX。
原因很简单：XXXX。
```

重点：
**不是只介绍产品，而是告诉读者“如果是我，我会怎么选”。**


# 18. “总结”格式

产品介绍之后，可以使用：

```
#### 总归来说：
```
或者：

```

```

```
### 总结：

- 千问：更偏通用 AI 助手
```

# 26. 语言风格

整体语言：

 **像一个有多年开发经验的资深程序员或者架构师在写博客。**
推荐：其实…… 比较有意思的是…… 这里需要注意…… 如果你是程序员…… 我个人更倾向于…… 简单理解…… 真正值得关注的是……
允许适当使用：“说白了” “其实” “比较有意思” “这个地方容易搞混” “我觉得” 但不要过度口语化。

# 27. 避免 AI 味

避免频繁使用： 综上所述 值得一提的是 在当今快速发展的时代 随着技术的不断发展 本文将深入探讨 不难发现 从多个维度来看
替换成：简单来说…… 这里真正需要注意的是…… 我觉得比较有意思的是…… 如果你实际用过就会发现……


# 28. 每个章节尽量回答一个问题

例如：
第一章： 国内 AI 产品有哪些？
第二章： AI Coding 工具有哪些？
第三章： 为什么这些工具都能选择 Qwen？
第四章： 这些模型有什么区别？
第五章： AI Agent 怎么收费？
第六章： 如果我是程序员，我应该怎么买？

而不是一个章节同时讨论五六个主题。

# 29. 推荐文章结尾

结尾不要写传统论文式总结。

推荐：
## 最后总结
- 如果只是简单体验： 
	XXX
- 如果是日常开发：
	XXX
- 如果是真正把 AI 当开发工具：
	XXX
- 对于后端 / 架构开发者，我个人更关注：

# 31. 核心原则

以后写这类博客，始终遵循：

```text
少一点定义
多一点场景

少一点官方介绍
多一点个人理解

少一点长篇文字
多一点表格

少一点复杂层级
适当的 Q&A

少一点“正确答案”
多一点“如果是我，我会怎么选”
````

最终目标不是写成一篇“百科”，而是让读者：

> **看完之后，知道这些东西是什么、有什么区别，以及自己到底应该怎么选。**
